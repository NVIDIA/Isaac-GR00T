# Insights Retrieval

Retrieve relevant evidence from the published, read-only `.insights/` projection and
return a concise handoff. The projection is prior knowledge, not proof of current
repository behavior.

## Required lookup

Use the deterministic retriever instead of searching the whole directory:

```bash
python skills/insights/scripts/search.py \
  --query '<exact symptom, version, embodiment, phase, and attempted fixes>'
```

The script searches upward from the current directory, so it finds a projection at the
monorepo root when invoked from `oss/`. It validates
`groot_insights_projection.v0`, reads only `index.json` and `nodes/*.json`, pairs
`finding:doc:X` with `doc:X`, and ignores `graph.html`, the viewer, and vendored
JavaScript.

Use `--insights-root <path>` only for an explicitly supplied projection. If the result
has `available: false`, report the grounding gap and continue the caller's workflow
without inventing knowledge.

## Grounding rules

- Use record IDs as stable citations. Prefer a finding with its paired chunk.
- Preserve the projection `generated_at` and SHA-256 in nontrivial handoffs.
- Treat unpaired, unscoped, stale, recommendation-only, or cross-version records as
  directional priors.
- Keep completed results separate from advice, hypotheses, pending work, and
  infrastructure failures.
- Do not combine incompatible models, tasks, datasets, metrics, configurations,
  platforms, or dates.
- Use current repository code and live incident evidence as the source of truth for
  present behavior.
- Never modify `.insights/`; it is regenerated by the reviewed publishing pipeline.

## Synthesis

Read the complete returned finding and chunk. If scope is missing from the record, say
so. When records conflict, report both and name the discriminating evidence needed.

Assign confidence to the synthesized claim:

- **High:** compatible, well-scoped direct results with supporting chunks;
- **Medium:** one direct, well-scoped result;
- **Low:** indirect, unpaired, stale, incomplete, or ambiguous evidence.

## Downstream Handoff

Return the smallest useful structure for the receiving agent. Use this fuller
contract when the result will feed another agent or a nontrivial decision:

```markdown
## Insight handoff

- Question: <the question or decision searched>
- Finding: <direct answer; distinguish evidence from inference>
- Confidence: <high|medium|low> — <brief reason>
- Scope: <model/task/dataset/metric/configuration/time represented>

### Evidence
- <claim or outcome> — `<finding id>` backed by `<chunk id or unpaired>`

### Caveats and conflicts
- <directional-only evidence, incompatible results, staleness, or none>

### Unknowns
- <missing evidence or none>

### Suggested downstream use
- <how the receiving agent can safely apply the finding>
```

Include experiment IDs, scores, baselines, statuses, and branch or artifact
pointers only when relevant to the decision. Keep each citation adjacent to the
claim it supports. Use repository-relative paths so the handoff remains
portable across worktrees.

Adapt the final section to the consumer:

- **FAQ:** Lead with a concise answer, keep experimental claims qualified,
  cite the best source sections, and identify unanswered parts. Do not present
  a research prior as product behavior or policy.
- **AutoResearch:** Separate ideas to build on, negative results to avoid,
  operational failures, pending experiments, and remaining hypotheses.
- **AutoDebug:** Separate observed symptoms, verified fixes, failed attempts,
  recommendations, and the next discriminating checks. Insights can rank a test but
  cannot support or defend a root-cause claim.
- **Post-training or evaluation:** Preserve exact variant, checkpoint, dataset,
  metric, and execution environment details; do not substitute nearby variants.

For a simple lookup, compress the handoff to a direct answer, one caveat if
needed, and the supporting citations.

## JSON projection sources (the `.insights/` JSON tree)

Most sources under `.insights/` are folders of markdown (handled by the workflow above).
Some are **structured JSON projections** — a redacted, read-only export of NVIDIA's internal
GR00T knowledge graph. The projection at the root of `.insights/` (`index.json` + `nodes/`)
is one: reviewed **findings** and the raw **chunks** they were distilled from. It is
*derived* (regenerated wholesale on each export), so it can lag the internal source but
never forks from it. Treat it as a curated evidence set, not a live database.

Two record kinds:

- **finding** — a short, human-reviewed takeaway ("what we learned").
- **chunk** — the raw, citable source passage a finding was distilled from, addressed by a
  stable `chunk_id`.

The machine-readable contract is `index.json` + `nodes/` only:

```
.insights/
├── index.json            # {schema_version, generated_at, topics[], findings[], chunks[]}
└── nodes/<topic>.json    # {topic,
                          #   findings: [{id, title, body, tags}],
                          #   chunks:   [{chunk_id, title, text, tags}]}
```

Read it **structurally**, not with `rg`:

1. Read `index.json` for the available `topics`.
2. Load the relevant `nodes/<topic>.json` (scan `general.json` and the closest topics when
   unsure).
3. Retrieve the findings/chunks whose `title` / `body` / `text` best match the question
   (keyword or embedding similarity over the loaded records).
4. Answer from the retrieved records only; cite each claim by its `finding.id` or `chunk_id`.

A finding and its source chunk share the same id suffix — `finding:doc:abcd` ↔ `doc:abcd` —
so cite the **finding** for the claim and its paired **chunk** for the exact quote. Content
is redacted (secrets/PII/partner lines stripped) and may lag; flag time-sensitive claims as
"as published, may lag". The grounding, ranking, reconciliation, and handoff rules above
apply unchanged.

A human-facing viewer ships with this skill under `scripts/` (`graph.html`, which fetches
`.insights/graph_data.json` at load, regenerated by `scripts/render_viewer.py`) — code and
data are kept separate. It is optional and for people only — agents answer *questions* from
the JSON, not from the viewer.

### Showing the graph to a human

If the user asks to **see / visualize / open / create** the graph (rather than answer a
question), treat it as an action: **(re)generate** the viewer from the current projection,
**serve** it over HTTP, and hand back the URL. The viewer `fetch()`es its JSON at load, so
`file://` will not work — always serve it:

```bash
python3 oss/skills/insights/scripts/render_viewer.py   # regenerate graph.html (scripts/) + .insights/graph_data.json
cd oss                                                 # data lives in oss/.insights/, so serve the oss/ dir
python3 -m http.server 8000                            # if 8000 is taken, pick another port (e.g. 8001)
# then open http://localhost:8000/skills/insights/scripts/graph.html
```

Report the `http://localhost:8000/skills/insights/scripts/graph.html` link (and note it
renders findings and their source chunks, filterable by node type). Do not paste raw JSON at
the user for a "show me" request; do not suggest opening `graph.html` directly via `file://`.

## No-Answer Behavior

If no relevant grounded evidence exists, report:

1. the exact query and projection hash, or the availability error;
2. the topics considered;
3. the missing fact or unresolved decision;
4. the best next source or owner to consult, if the repository identifies one.

Do not claim that the answer does not exist outside the searched corpus. Do not
invent a fallback contact, result, or recommendation.
