# GR00T Onboarding

Use the local OSS CLI for training, evaluation, serving, and deployment.
AutoDebug and AutoResearch use their own documented skill interfaces. Do not
substitute internal OSMO, GitLab pipelines, internal agents, or golden-run
workflows for ordinary local OSS execution.

Invoke `$onboarding` to present the menu. For a direct tour, setup, or
feature request, skip the menu and read
[references/feature-help.md](references/feature-help.md). Reuse the user's
inputs and execution authorization; a full training smoke is not a prerequisite
for another workflow.

## Generate the CLI-style chat interface

For general onboarding, “show me the menu,” or an explicit interface request,
present a compact terminal-style menu inside a fenced `text` block in chat.
The agent generates it from the current `groot/infra/oss.py` entrypoint; do not
maintain a separate command registry or treat a sample menu as authoritative.

1. Locate the OSS package root: the directory containing `pyproject.toml` and
   `groot/infra/oss.py`. In the upstream monorepo this is `oss/`; in the exported
   repository it is the repository root. Run every CLI command from that
   directory so repository guidance and skills resolve within the OSS tree.
   Read `_parse_args` in `groot/infra/oss.py` as text, then the parser helpers
   it calls, including imported helpers such as
   `groot/infra/closed_loop/cli.py`. Use file-reading tools or text search; do
   not import modules, run Python or uv, invoke runtime `--help`, or probe
   installed packages to discover the menu. There is no environment preflight
   for browsing, so missing NumPy or other runtime dependencies are irrelevant.
2. Generate one numbered row for each actual subcommand, in parser registration order. Keep
   its exact command name and add a short user-facing description based on its
   parser `help=` text. Add `tour` and `setup` as chat navigation choices, clearly separated
   from executable subcommands. Include the `Agent workflows` choices described
   below, separated from the generated CLI commands. Read their skill
   descriptions as text; do not run either workflow just to construct the menu.
   Show `help <command-or-workflow>`, `back`, and `status` as
   chat controls. Do not imply these controls are `oss.py` commands.
3. Accept a number, exact command name, agent-workflow alias, or plain-language goal. Keep the displayed
   number-to-command mapping in the conversation until the menu is regenerated.
   An unknown selection redisplays the choices; it must not execute a command.
   Direct task requests bypass the menu and follow the selected workflow.
4. For a selected command, read its parser source and relevant feature guide
   as text. Follow `add_argument` definitions, parser defaults, validators, and
   referenced constants to identify supported options and conditional inputs. Collect missing required inputs in a compact prompt;
   reuse values already supplied. Offer relevant optional settings rather than
   dumping all flags. Generate conditional inputs from both the parser and guide:
   for example, `train-eval --benchmark-recipe` owns its settings, while ordinary
   train-eval needs a dataset and embodiment. List available recipe IDs from the
   checked-in specs when the user chooses that mode. TensorRT acceleration is an
   option only on the inference commands that expose it; `build-trt` is its own
   command and has no dry-run. Never invent flags or subcommands.
5. Show the resolved command and the expected output before execution. Apply the
   selected workflow's normal execution rules and existing user authorization;
   selecting a help or navigation choice performs no installation or GPU run.
   Keep missing inputs visible rather than inventing paths, hardware, or access.
6. `help <command-or-workflow>` explains its inputs, outputs, and supported options
   or execution limits by reading source and skill instructions. `back`
   returns to the menu without cancelling an active job. `status` summarizes
   known inputs, actual resolution/execution state, artifacts, and active jobs.
   Never fabricate terminal logs, progress bars, hardware checks, or results.
   After execution, report verified results or the first failure in the same
   compact style and offer the relevant next action.

## Agent workflows

Always display these choices in a separate `Agent workflows` section:

```text
debug      Investigate a failure with AutoDebug
research   Improve a working recipe with AutoResearch
```

These are chat aliases for skills, not `oss.py` subcommands. Include them in the
same selection flow; `help debug` and `help research` explain the workflows
without launching them. Natural-language requests route the same way. Continue
in the current conversation by reading and following the selected skill.

- `debug`, `autodebug`, or a request to investigate an unexplained repository
  failure: use [AutoDebug](../autodebug/SKILL.md). Carry the user's goal, exact
  command, checkout/revision, environment facts, first failure and available
  logs/artifacts, checks already tried, and granted compute/access. Reuse any
  existing incident or report. Let AutoDebug normalize its report and conduct
  the evidence loop; report unavailable facts as unknown. Preserve the user's
  diagnosis-versus-fix scope and follow AutoDebug's verification rules.
- `research`, `autoresearch`, or a request to improve a working recipe: use
  [AutoResearch](../autoresearch/SKILL.md). Carry the config/study path and state
  when present, train/eval commands or wrappers, dataset and checkpoint paths,
  baseline commit/result, metric and direction, research ideas and constraints,
  compute target, trial budget, and prior execution authorization. Collect only
  missing inputs. If the baseline contract is incomplete, follow AutoResearch's
  route to [baseline preparation](../prepare-autoresearch-baseline/SKILL.md).
  Selecting `research` starts preparation or validation; launch, resume, or smoke
  execution requires the user's explicit request under the AutoResearch rules.
- A failure within an existing AutoResearch study stays with AutoResearch for
  study inspection and diagnosis. An unrelated repository failure routes to
  AutoDebug. Routine setup questions stay in onboarding. Do not start diagnosis
  merely because a user asks what a workflow does.

Browsing these choices is Python-independent. Runtime requirements for actual
agent-workflow execution come from the selected skill. Return its verified
result, state or incident path, and next action; do not claim that routing alone
has completed the investigation or improved a recipe.

The menu, tour, option explanations, and command drafting require only repository
text files: no Python installation, uv environment, GPU, dataset, or credentials.
Check or install a runtime only when the user selects setup or requests actual
command resolution (a dry run) or execution. Those operations still require the
selected workflow's Python dependencies; do not report a drafted command as a
successful dry run. A menu request is complete
when the current choices are presented and the agent waits for the user's
selection. It does not require creating a terminal application or new launcher.

Work from the OSS package root and follow `AGENTS.md`. Use the
[feature checklist](../../docs/agentification.md) to find each command's guide.
For `tour`, `setup`, or execution help after selection, read the corresponding
mode in [references/feature-help.md](references/feature-help.md); do not
regenerate the menu unless requested. The selected workflow's success checks determine completion.
